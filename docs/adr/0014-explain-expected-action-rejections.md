# Expected action rejections remain explainable

Game rules distinguish an expected **rejection** from an unexpected **failure**. Authoritative rule checks expose an allowed/rejected outcome and a stable, centrally declared `StringName` reason code rather than collapsing every outcome to `false` or embedding player-facing copy. One feedback-owned catalog translates those reasons into warm, terse explanations; widgets provide only the reason and visual anchor. Dynamic fact payloads are deferred, so initial copy does not promise values such as the exact Biomass shortfall. Presented actions with useful, recoverable constraints may look unavailable while remaining interactive enough to explain themselves, while modal locks, nonexistent features, and safety constraints remain truly disabled or hidden.

Rejection feedback stays local to the attempted action whenever possible: a small non-color-only motion or shape response plus an anchored reason, with an optional remedy when it adds useful guidance. Invalid drags signal their blocked state on hover and acknowledge release; repeated attempts refresh one message instead of stacking and rate-limit stronger motion. When more than one rule rejects an action, the system reports only the first fundamental cause: intrinsic actor/item eligibility, then target state/capacity, run safety, and finally resources. Global feedback is a fallback for actions without a meaningful screen location, and expected rejection feedback never masks transaction rollbacks or invariant violations.

The first rollout incrementally replaces boolean checks for Adult-to-Cocoon eligibility, Mutation capacity, regular Fertilizer capacity, and insufficient Biomass on Nursery Shop reroll; temporary boolean helpers may delegate to the new result checks while unrelated systems migrate later. Its first catalog maps `ONLY_CHILD_CAN_TRAIN` to “Only child units can be trained.”, `MUTATION_CAPACITY_FULL` to “Mutation capacity full”, `FERTILIZER_CAPACITY_FULL` to “Fertilizer capacity full.”, and `NOT_ENOUGH_BIOMASS` to “Not enough Biomass.” Rejection explanations remain active when tutorials are disabled because they are operational feedback, not coaching. The core contract remains input-agnostic, but the pilot adds only mouse and drag/drop adapters because the management loop has no complete keyboard, controller, or touch interaction path yet. The shared presentation is a dedicated screen-fixed layer above normal HUD content and below detail tooltips and scene transitions: a compact, input-ignoring paper-tag callout with a warm warning accent, blocked symbol, brief local nudge, and a roughly 1.5–2 second lifetime. It dismisses when its anchor exits, its Base screen changes, or a scene transition begins. An unmapped reason displays “Action unavailable” in release while raising a developer error. The pilot succeeds when every rejected action preserves state and items, visibly acknowledges input beside its cause, stays calm under repetition, uses the same authoritative result for preview and execution, and leaves unexpected failures on the developer-error path. Verification uses direct rule checks, a Godot boot, and a focused manual interaction matrix rather than introducing a test framework. Rejection telemetry is deferred until the interaction is stable, but reason codes remain suitable for later aggregation.

After the pilot, rollout prioritizes apparently valid actions that currently fail silently: buying with full Stock, harvesting with a full Troop, moving a Unit into a full destination, planting with no empty Plot, composting the last available fighter, and starting a Battle with an empty Squad. Hidden unavailable features and already-clear locked-price states remain lower priority.

## Considered Options

We rejected generic “Not allowed” feedback because it acknowledges input without teaching the governing rule, widget-side rule inference because it will drift from authoritative game logic, and global toasts as the default because they separate the explanation from its cause.
